# 机房设备运维助手（DeviceLedger）

**用一句中文问设备的事，程序自己去机房台账里查，再用中文回答你。**

值班员不用记接口、不用点菜单、不用翻 Excel —— 在命令行里打字问就行。

---

## 它解决什么问题

机房值班员每天重复问的其实就三句话：

- 「3 号机架那台交换机现在什么状态？」
- 「现在有几台设备是故障状态？」
- 「这台设备过保了没？」

传统做法是打开 Excel 或管理系统，一层层点到设备列表里去看。这个项目把这几个高频问题变成「问一句」。

**和普通聊天机器人的区别：所有答案都来自真实数据库，不是模型编的。** 模型只负责「听懂你在问什么」和「把结果说成人话」，中间那一步查数据，走的是我自己写的接口。

---

## 效果

```
>> 核心交换机现在什么状态

① 它想调：device_status
② 参数：{"name": "核心交换机"}
③ 接口回了：{'found': True, 'location': '3号机架', 'status': '正常'}

核心交换机当前状态是**正常**，位于 **3号机架**。
```

```
>> 核心交换机坏了

① 它想调：report_fault
② 参数：{"name": "核心交换机"}
③ 接口回了：{'ok': True, 'name': '核心交换机', 'status': '故障'}

已把「核心交换机」的状态改为**故障**。
```

## 架构：三层，一层一个文件

```
┌─────────────────────────────────────────────┐
│  你：用中文问一句话                          │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│  agent_ops.py —— Agent 层                    │
│  · 把问题 + 6 个工具清单交给大模型            │
│  · 大模型回 tool_calls（要调哪个、参数是什么）│
│  · 按路由表 methods 调对应接口               │
│  · 把接口结果塞回 messages，再问一次大模型     │
│  · 大模型用中文回答                          │
└──────────────────┬──────────────────────────┘
                   ↓ HTTP（本地 8001 端口）
┌─────────────────────────────────────────────┐
│  api_ops.py —— 接口层（FastAPI）             │
│  6 个接口，每个对应值班员的一句话            │
└──────────────────┬──────────────────────────┘
                   ↓ SQL
┌─────────────────────────────────────────────┐
│  ops_db.py / ops.db —— 数据层（SQLite）      │
│  表 devices：id / name / location /          │
│              status / warranty_end           │
└─────────────────────────────────────────────┘
```

**为什么分三层而不是写一个文件：**
接口层可以脱离 Agent 单独用（`/docs` 里能直接点），Agent 层可以换个模型而不用改数据库代码。层与层之间只通过 HTTP 和 SQL 说话。

## 6 个接口

| 接口 | 方法 | 参数 | 回答什么 |
| --- | --- | --- | --- |
| `/device_status` | GET | `name` | 这台设备在哪、什么状态 |
| `/fault_count` | GET | — | 现在有几台是故障 |
| `/expired_devices` | GET | — | 哪些设备已经过保 |
| `/device_count` | GET | — | 台账里一共几台设备 |
| `/warranty_status` | GET | `name` | 这台过保了没（算出来的，不是存着的） |
| `/report_fault` | **POST** | `{"name": "..."}` | 把这台设备标成故障 |

**Agent 侧的 6 个工具和这 6 个接口一一对应**，路由表 `methods` 记录每个工具该用 GET 还是 POST：

```python
methods = {
    "device_status":   "get",
    "fault_count":     "get",
    "expired_devices": "get",
    "device_count":    "get",
    "report_fault":    "post",   # 唯一会改数据的
    "warranty_status": "get",
}
```

## 怎么跑起来

```bash
# 1. 装依赖
pip install fastapi uvicorn requests python-dotenv

# 2. 建库 + 插 5 台测试设备
python ops_db.py

# 3. 起接口服务（另开一个终端）
uvicorn api_ops:app --port 8001

# 4. 跑 Agent（需要 DeepSeek API Key，写在 .env 里）
python agent_ops.py
```

`.env` 里放一行：

```
DEEPSEEK_API_KEY=sk-你的key
```

`.env` 已在 `.gitignore` 里，不会被提交。

## 技术栈

- **Python 3.12**
- **FastAPI** —— 接口层，自带 `/docs` 交互文档
- **SQLite** —— 单文件数据库，`ops.db`
- **DeepSeek API** —— Tool Calling（工具调用），不使用任何 Agent 框架

> 没有用 LangChain 之类的框架，是因为想把 Tool Calling 的循环自己写一遍：
> 工具清单 → `tool_calls` → 解析参数 → 调自己的接口 → 结果回传 → 再问一次 → 出人话。

## 三个刻意的设计选择

**1. 接口说真话。** 查不到设备就返回 `{"found": false}`，不返回空对象硬编一个答案。状态改失败就返回 `{"ok": false}`。程序宁可说「没有」，也不假装成功。

**2. `warranty_end` 存日期，过保与否算出来。** 表里只存到期日 `2026-06-30`，是否过保用 `warranty_end < date('now')` 现场比较。存一个 `is_expired` 字段会过时——今天算对，明天就错了。

**3. 多轮循环 + 保险丝。** 大模型可能一次要调好几个工具，也可能反复调。`while` 管轮数（最多 10 轮）、`for` 管条数（一次几个工具都遍历），超过上限就停，避免死循环烧 API。
